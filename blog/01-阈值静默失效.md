# 我给一个营养阈值调了三次版本，第三次才发现自己一直在算错

> 项目：https://github.com/yftu/mcd-triple-target
> 起因：给麦当劳 MCP 写了个配餐 Skill，结果被自己的"科学假设"坑了三轮

## 一、先说结论

这个 bug 从来没有报过错。

没有异常抛出，没有堆栈，没有数据崩溃。它安静地躺在那里，让我的"低钠优选"功能**完全不生效**，而我盯着输出看了很久，还以为算法是对的。

---

## 二、我最初在做什么

用麦当劳官方的 MCP 数据做配餐推荐，`list-nutrition-foods` 一次能返回 160 条餐品的完整营养信息。

目标是三目标寻优：热量、蛋白质、预算。评分函数长这样：

```python
score = 0.42 * 热量得分 + 0.36 * 蛋白得分 + 0.22 * 预算得分 + bonus
```

`bonus` 里有一项是钠惩罚。我按营养学常识定了个阈值：

```python
def _slim_penalty(item):
    """成人每日钠建议摄入 <2000mg，单餐不宜超过 800mg"""
    return max(0, (item.sodium - 800) / 400)
```

看起来很合理：800 mg 是常见的单餐上限建议，超了就扣分。

**然后我把它跑在了真实的 160 条数据上。**

---

## 三、第一次翻车：惩罚几乎不生效

跑完真实数据，我统计了一下有多少餐品吃到了惩罚：

```
超过 800mg 的餐品占比：18.2%
```

哦豁，只有 18% 吃到了惩罚。听起来还行？

不对。我当时想的是"那 82% 的餐品都是低钠的好选择"，**但实际上我的数据里 82% 的餐品钠含量都低于 800mg——这意味着对于绝大多数餐品，这个惩罚项压根不存在**。

**它不是"惩罚了大多数人"，而是"对大多数人完全无效"。** 我需要的是能拉开差距的指标，不是一个几乎恒为 0 的常量。

于是我改了个"更科学"的值。参考《中国居民膳食指南》，钠摄入建议不超过 2000mg/天，集中在一餐偏多，所以取 1400mg：

```python
return max(0, (item.sodium - 1400) / 300)
```

1400 mg。**七成的每日建议量，看起来非常合理。**

---

## 四、第二次翻车：它变成了死代码

改完之后我重新统计：

```
超过 1400mg 的餐品占比：0.0%
```

**零。**

我以为是统计脚本写错了，回头查原始数据：

```
钠含量分布（160 条真实数据）
最小 1 mg ｜ P25 80 ｜ 中位 147 ｜ P75 705 ｜ 最大 1373 mg
```

**全表最大值是 1373 mg。我的阈值是 1400 mg。**

这个惩罚项永远不会触发。它不是"效果不好"，它是**一段永远返回 0 的死代码**。

而最可怕的地方在于：**它没有任何异常。**

- 没有报错
- 没有警告
- 测试全绿
- 输出格式完全正常

我要是没顺手统计一下分布，这个函数会一直躺在代码里，直到比赛结束都不会有人发现。

---

## 五、第三次：让数据决定阈值

我决定不再猜了，直接用真实分布来定阈值。

从上面那组数据看，P75 = 705 mg，意味着约 25% 的餐品超过这个值。取 600 mg（约 P70）为基准，每超 250 mg 记 1 分：

```python
def _slim_penalty(item):
    """阈值 600mg 来自官方 160 条真实数据的 P70，
    而非营养学建议值——800 时命中率仅 18%，
    1400 时命中率为 0（高于全表最大值 1373mg）。"""
    if item.sodium <= 0:
        return 0.0
    return max(0.0, (item.sodium - 600) / 250)
```

| 版本 | 阈值 | 命中率 | 问题 |
|:---:|---:|---:|---|
| v1 | 800 mg | 18.2% | 恰等于 P75，区分度不足 |
| v2 | 1400 mg | **0%** | **高于全表最大值，代码永不执行** |
| v3 | **600 mg** | ~25% | 采纳 |

## 六、这件事的真正教训

**不是"要小心写代码"，而是：**

### 1. 常识性阈值必须用真实数据回归验证

我两次都是"按营养学常识"定的值，两次都错了——一次太松，一次太紧。数据分布才是唯一的事实来源。

### 2. 静默失效比崩溃危险得多

崩溃会告诉你哪里错了。静默失效让你**以为自己是对的**，然后基于错误的结果继续做决策。

如果我在做严肃的健康类产品，这个 bug 可能一直存在。

### 3. "看起来更科学"是个陷阱

1400 mg 看起来比 800 mg 更专业——它是七成的每日建议值，是一个"有依据"的数字。但正因为它听起来合理，我甚至没怀疑过要验证。

**越是"有依据"的数字，越容易让人停止思考。**

## 七、附带发现：加权评分也有这个问题

修完钠阈值，我在做演示动画时又撞上另一个 bug。

增肌场景下，算法给我推了这个：

```
· 双层深海鳕鱼堡  485 kcal  蛋白 28 g  ¥22
· 麦乐鸡5块       213 kcal  蛋白 12 g  ¥11
· 冰美式小杯        15 kcal  蛋白  0 g  ¥10   ← 占预算却几乎无营养
· 圆筒冰淇淋93 kcal  蛋白  2 g  ¥6
```

"冰美式 + 冰淇淋"占了 22 块，只贡献 15 kcal 和 2 g 蛋白。

**这次不是搜索 bug，是目标函数被套利了：**

- 冰淇淋热量低 → 拉低总热量 → **热量项得分虚高**
- 冰淇淋便宜 → 拉低总花费 → **预算项得分受益**

单独看每项都不算离谱，叠加之后，"低热量 + 便宜"的零食反而成了最优解。

我加了两项**与目标正交**的结构性约束：

```python
# 蛋白能量占比惩罚：低于 55% 标准参考时计罚
protein_share = protein_total / (kcal_total / 4.0)
if protein_share < 0.55:
    bonus -= (0.55 - protein_share) * 45.0

# 低热量密度单品（≤120kcal，多为饮料/冰品）占比超过 28% 时计罚
snack_kcal = sum(i.kcal for i in items if i.kcal <= 120)
if snack_kcal / kcal_total > 0.28:
    bonus -= (snack_kcal / kcal_total - 0.28) * 90.0
```

修完后，**控卡场景的结果完全没变**——这说明新约束没有破坏原有合理方案，是合格的回归。

## 八、另一个坑：MCP 返回不是 JSON

顺便说个更基础的。麦当劳 MCP 的工具返回**不是纯 JSON**，而是四层嵌套：

```
Markdown 字段说明（含 {序号} 占位符）
  ↓ "## Original Response" 分隔符
JSON 字符串
  ↓ obj["data"] 仍是字符串
toon 紧凑格式表格 ← 160 条记录
  ↓ 按列名 + 行记录
结构化数据
```

两个具体的坑：

**坑一：说明文字里有 `{序号}` 占位符**，粗暴取首个花括号会解析失败。得用括号配对 + 字符串转义感知扫描。

**坑二：toon 行内字段可能含逗号**，直接 `split(',')` 会错列。

```python
# 逗号数恰好匹配则直切，否则从右向左按列数反向定位分隔符
def _split_toon_row(line, ncols):
    if line.count(",") == ncols - 1:
        return line.split(",")
    parts, rest = [], line
    for _ in range(ncols - 1):
        pos = rest.rfind(",")
        if pos == -1:
            break
        parts.insert(0, rest[pos + 1:])
        rest = rest[:pos]
    return [rest] + parts
```

实测 160 / 160 条 100% 解析成功。
