## 四、钠分布（sodium）—— 阈值标定的依据

| 指标 | 值 (mg) |
|---|---|
| 最小 | 1 |
| P25 | 80 |
| **中位数** | **147** |
| P75 | 705 |
| 最大 | 1373 |
| >800 mg 的条目占比 | **18.2 %** |

### 三次阈值迭代记录

| 版本 | 基准值 | 惩罚命中率 | 问题诊断 |
|---|---|---|---|
| v1 | 800 mg | 约 18% | 基准恰等于 P75，绝大多数餐品惩罚为 0，区分度弱 |
| v2 | 1400 mg | **0%** | **全表最大值仅 1373 mg，惩罚项完全失效，成为死代码** |
| v3 | **600 mg** | 约 25% | 最终采纳 |

**v2 的失败最具警示意义**：1400 mg 这个值在纸面上更"科学"（约占成人每日建议 2000 mg 的七成），但它完全脱离了真实数据分布。这类 bug 不会抛异常、不会崩溃，只会让优化目标静默地不起作用。

**结论**：任何基于营养学常识设定的阈值，都必须用目标数据集回归验证后再采纳。这是本项目最核心的一条工程经验。

## 五、组合逻辑的二次修正：零食组合问题

### 问题发现

生成演示动图时，算法在增肌场景下输出了这样的方案：

```
· 双层深海鳕鱼堡  485 kcal  蛋白 28.0 g  ¥22.0
· 麦乐鸡5块       213 kcal  蛋白 12.0 g  ¥11.0
· 麦辣鸡翅         224 kcal  蛋白 13.0 g  ¥13.0
· 冰美式小杯15 kcal  蛋白  0.0 g  ¥10.0
· 圆筒冰淇淋       93 kcal  蛋白  2.0 g  ¥6.0
```

**「冰美式 + 冰淇淋」占了 22 元，却只贡献 15 kcal 热量和 2 g 蛋白。**

### 根因分析

这不是搜索 bug，而是**目标函数的设计盲区**。三个加权分项各有偏好：

| 分项 | 对该组合的表现 |
|---|---|
| 热量项 | 冰淇淋热量低（93 kcal），拉低了总热量 → 分母变小，**热量得分虚高** |
| 蛋白项 | 贡献 2 g 蛋白，几乎无影响 |
| 预算项 | 便宜，占预算 22 元 → 拉低总花费，**得分受益** |

单独看每项都不算离谱，叠加后「低热量 + 便宜」的零食反而成了得分最优解。**加权归一化的加权目标，在无硬约束时天然存在这类结构性套利。**

### 修正方案

在评分函数末尾追加两项**与目标无关**的结构性惩罚：

```python
# 蛋白能量占比惩罚：低于 55% 标准参考（4 kcal/g）时递减计罚
protein_share = protein_total / (kcal_total / 4.0)
if protein_share < 0.55:
    bonus -= (0.55 - protein_share) * 45.0

# 低热量密度单品（≤120 kcal，多为饮料/冰品）占比惩罚：超过 28% 时计罚
snack_kcal = sum(i.kcal for i in items if i.kcal <= 120)
if snack_kcal / kcal_total > 0.28:
    bonus -= (snack_kcal / kcal_total - 0.28) * 90.0
```

第一项防止"低蛋白密度"方案在控卡场景钻空子，第二项防止"纯零食凑单"在任何目标下胜出。

### 修正效果

| 场景 | 修正前 | 修正后 |
|---|---|---|
| 控卡减脂 | 巨无霸 + 麦辣鸡翅 | **不变**（747 kcal / 蛋白 38 g） |
| 增肌补充 | 含冰美式 + 冰淇淋 | 正餐占主导，饮品甜品仅在预算有余时出现 |

控卡场景未受影响，说明新增惩罚项没有破坏原有合理方案——这正是**回归测试应达到的效果**。

### 教训

加权归一化的评分函数要防住结构性套利，光靠调整权重不够，必须补充**与优化目标正交的约束项**。这类问题往往在可视化呈现时才暴露，纯看数字输出不容易发现。

## 六、字段可用性说明

| 字段 | 可用性 |
|---|---|
| `productName` | 100% 可用 |
| `energyKcal` / `energyKj` | 100% 可用 |
| `protein` / `fat` / `carbohydrate` | 100% 可用 |
| `sodium` / `calcium` | 100% 可用 |
| `nutritionDescription` | **几乎全为 null**，不可依赖 |

`nutritionDescription` 字段在实测中几乎全部返回 `null`，因此本项目未使用该字段。所有营养计算仅基于 5 项宏量营养素字段。

## 六、数据局限

1. **价格不在营养表中**。营养数据不含价格，必须通过 `query-meals` 按门店实时获取，本项目严格使用 MCP 返回的真实价格，不做估算。
2. **可售状态随门店与时段变化**。同一餐品在不同门店、不同时间可能不可售，方案输出时应提示用户以门店实际供应为准。
3. **套餐与单点差异**。营养表按单品给出，套餐可能组合不同规格的汉堡与小食，热量需通过 `query-meal-detail` 展开后重新核算。
4. **数据会变**。菜单与营养数据随季节、地区、门店调整，本文件中的分布结论对应提交时状态。解析器已对表头变化做了容错，但阈值需在数据大幅变动后重新标定。
